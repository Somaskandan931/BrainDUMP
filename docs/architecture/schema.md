# Database Schema

SQLite via SQLAlchemy 2.0 declarative models (`Mapped` / `mapped_column`).
Engine, session factory, and `init_db()` live in `backend/database.py`.

## Entity-relationship overview

```
Project (1) ───< (many) Task ───< (many) Subtask
                         │  │
                         │  └───< (many) WorkSession >─── (0/1) CalendarEvent
                         │
                         ├───< (many) Prediction
                         │
                         └───< (many) Dependency >───┘  [task_id / depends_on_task_id, both self-FK to tasks]

CalendarEvent (0/1) ───< (many) WorkSession   [optional link, see below]

ProductivityMetric   — standalone daily rollup, not FK'd to anything
Setting              — standalone key/value store
EpisodicMemory       — standalone durable event log (PRD §63)
SemanticMemory       — project relationships/templates, FK'd to Project (subject/object), (PRD §63)
```

## Tables

| Table | Purpose | Key columns |
|---|---|---|
| `projects` | Groups related tasks | `name`, `status`, `goal_text` (set if generated by the Goal Engine) |
| `tasks` | Central work item | `project_id` (nullable — standalone tasks allowed), `status`, `importance`, `energy_requirement`, `deadline`, `estimated_hours`/`actual_hours`, `confidence_score`, `priority_score`, `context_switch_cost` |
| `subtasks` | AI Task Breakdown output | `task_id`, `title`, `status`, own `estimated_hours`/`actual_hours` |
| `work_sessions` | Ground-truth timer/focus sessions | `task_id`, `calendar_event_id` (nullable), `start_time`/`end_time`, `duration_minutes` vs `predicted_duration_minutes` |
| `calendar_events` | Local cache of Google Calendar + Brain-Dump-created blocks | `task_id` (nullable), `google_event_id` (unique, for sync reconciliation), `source`, `sync_status` |
| `predictions` | Estimator/Priority training log | `task_id`, `category`, `predicted_hours` vs `actual_hours`, `error_pct`, `predicted_priority_score` |
| `dependencies` | Task dependency graph (PRD §31/§62/§61 ERD) — `task_id` can't proceed/complete until `depends_on_task_id` does | `task_id`, `depends_on_task_id` (both self-FK to `tasks`, unique pair). Read by `services/scheduler_service.py` to topologically order work; written by `services/planner_service.py`'s `generate_from_goal()`, which chains sequential tasks only when the goal-breakdown model supplied explicit, strictly-increasing `order` values (see `_record_sequential_dependencies`). |
| `productivity_metrics` | Daily rollup for Analytics/Weekly Review | `date` (unique), `hours_worked`, `completion_rate`, `most_productive_hour`, `estimation_error_pct` |
| `settings` | Generic key/value preferences | `key` (unique), `value` (JSON-encoded text) — also where `ai/long_term_memory.py` persists the computed Long-Term Memory profile (PRD §63), under key `long_term_memory_profile` |
| `episodic_memory` | Durable event log — Episodic Memory tier (PRD §63): weekly reviews, completed projects, milestones, planning decisions | `event_type`, `occurred_on`, `title`, `summary`, `payload` (JSON-encoded text). Written by `ai/episodic_memory.py`'s `record_event()`, deduped per `(event_type, occurred_on, title)` so re-computing the same real-world event (e.g. viewing the same week's review twice) updates one row instead of duplicating it. `MILESTONE` events specifically are written by `services/scheduler_service.py::complete_task()` — a project's completed-task ratio crossing 25/50/75/100% (only tracked for projects with at least `_MILESTONE_MIN_PROJECT_TASKS` tasks, so the threshold means something), distinct from `PROJECT_COMPLETED` which only fires on the explicit `Project.status` transition, not on task count. |
| `semantic_memory` | Project relationships — Semantic Memory tier (PRD §63): templates and recurring workflows | `relation_type` (`project_template` \| `recurring_workflow`), `subject_project_id`/`object_project_id` (nullable FKs to `projects`), `title`, `summary`, `payload` (JSON-encoded text). Written by `ai/semantic_memory.py` on project completion: `PROJECT_TEMPLATE` captures a completed project's task breakdown + its own dependency chain; `RECURRING_WORKFLOW` links it to an earlier project when task-title token overlap crosses a similarity threshold. Deduped per `(relation_type, title)`. No standalone `project_dependency` relation type — see the module docstring for why. |

All tables inherit `created_at` / `updated_at` (UTC, auto-managed) from
`TimestampMixin` in `models/mixins.py`.

## Migrations (Alembic)

Schema changes are Alembic migrations in `backend/migrations/versions/`
(baseline: `0001`). `database.init_db()` runs on every boot: a DB with an
`alembic_version` table gets `upgrade head`; a new file, or a DB from before
Alembic, gets tables created, missing columns synced (the old stand-in), and
is then stamped at head.

```
alembic revision --autogenerate -m "add foo to tasks"   # from ai_os/, after editing a model
python -m backend.migrate                                # apply to data/tasks.db (also happens on boot)
alembic downgrade -1
```

`tests/test_migrations.py::test_migrations_match_the_models` fails if a model
changes without a matching migration. SQLite can't ALTER most things in place,
so `env.py` uses batch mode — review autogenerated migrations before committing.

## Design notes

- **`Task.project_id` is nullable.** A brain dump like "Gym tomorrow" is a
  valid task with no project — matching the PRD's brain-dump examples.
  Every other FK to `tasks.id` cascades on delete, so removing a task
  cleans up its subtasks, sessions, calendar events, and predictions.
- **`Subtask` is a separate table, not a self-referential `Task`.**
  Subtasks don't carry a priority score or energy requirement — they
  inherit urgency from the parent task, and keeping them a distinct,
  simpler model matches how the AI Task Breakdown agent emits them
  (see `AGENTS.md`).
- **`WorkSession` is the ML ground truth.** `predicted_duration_minutes`
  is set at scheduling time; `duration_minutes` is filled when the
  session ends. `ml/estimator.py` (see `ANALYTICS.md`) trains directly
  on this pair rather than on `Task.estimated_hours`/`actual_hours`,
  which are denormalized convenience fields updated from sessions.
- **`CalendarEvent` serves two roles**: a local cache of pulled Google
  Calendar events (`source=GOOGLE`, for fast free/busy lookups) and
  scheduler-created work blocks pushed outward (`source=BRAIN_DUMP`,
  tracked via `sync_status`). `google_event_id` is unique and nullable
  so local-only events don't collide.
- **Enums are Python `str, enum.Enum`** (`models/enums.py`) so values
  serialize cleanly to JSON for the FastAPI layer without a custom
  encoder, while still being validated at the DB layer via
  SQLAlchemy's `Enum` type.
- **No external task-service table.** A `Task.todoist_id` column was
  added for Todoist reconciliation and later removed when Todoist sync
  was dropped in favor of a native task manager.

## Verified

This schema was validated by running `init_db()` against a throwaway
SQLite file, inserting a `Project` → `Task` → `Subtask` → `WorkSession` →
`Prediction` chain, and reading it back through the ORM relationships.
All 8 tables and foreign keys came up as designed.

`dependencies` and `semantic_memory` (added in later passes, no network/
DB access available) were checked with `py_compile` + a full AST sweep
and manual review against the conventions above, not a live `init_db()`
run — worth a real smoke test before trusting them in production.
