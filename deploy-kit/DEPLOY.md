# Deploying Brain Dump — Netlify (frontend) + Render (backend)

This app was built local-first (SQLite, in-process scheduler, local
Ollama), so a few things need to move off "assume everything is on one
laptop" before it works split across two hosts. The three code changes
below are already made; everything else is host configuration.

## What changed in the code (already done)

- `backend/app.py` — CORS origins now come from `ALLOWED_ORIGINS` (env
  var, comma-separated) instead of being hardcoded to
  `http://localhost:3000`.
- `backend/config.py` — `OLLAMA_HOST` / `OLLAMA_MODEL` read from env vars
  so they can point at Render's private Ollama service. Google Calendar is
  now a per-user web OAuth flow configured through `GOOGLE_CALENDAR_*`
  env vars (see below) — there is no shared `credentials.json`/`token.json`
  file anymore.
- The deploy-kit's `app.py`, `config.py` and `requirements.txt` are the
  current multi-user backend (auth router, JWT settings, auth dependencies)
  plus the deploy-specific bits; copy all three over the backend as-is.

## The real blocker: Ollama

`qwen3:8b` needs ~6-8GB RAM just to load, with no GPU on Render. Two
honest options:

1. **Run it anyway.** `render.yaml` includes a `brain-dump-ollama`
   private service sized on Render's `standard`/`pro` plan. Works, but
   costs real money per month and inference will be noticeably slower
   than your local Ollama.
2. **Swap to a smaller model** (`qwen2.5:1.5b`, `phi3:mini`, etc.) by
   changing `OLLAMA_MODEL` in `render.yaml` and
   `deploy/ollama/Dockerfile`. Cheaper and faster, but check output
   quality against your prompts in `backend/ai/prompts.py` before
   committing to it — smaller models follow the JSON-mode contract your
   agents expect less reliably.

There's no way around picking one of these — a hosted, always-on Ollama
is unavoidably a bigger box than a hosted Postgres-sized API.

## 1. Repo layout

Render and Netlify both build from one GitHub repo, so combine what
you have into a single repo with this top-level layout (your three
folders map straight onto it):

```
/
├── backend/          (from BACKEND.zip)
├── frontend/          (from FRONTEND.zip)
├── tests/              (from ROOT-tests-and-alembic.zip)
├── alembic.ini          (from ROOT-tests-and-alembic.zip)
├── pytest.ini
├── deploy/ollama/       (new — Dockerfile + entrypoint.sh)
├── render.yaml           (new)
└── backend/Dockerfile     (new)
```

Push that to GitHub before touching Render or Netlify — both deploy
from a repo, not a zip upload.

## 2. Backend — Render

**Option A (Blueprint, recommended):** Render dashboard → New →
Blueprint → select your repo. It reads `render.yaml` and creates both
`brain-dump-backend` and `brain-dump-ollama` for you.

**Option B (manual):** create two services by hand using the same
settings `render.yaml` specifies (Dockerfile path, disk, env vars).

Either way, before the first deploy:

1. Edit `render.yaml`'s `ALLOWED_ORIGINS` value to your real Netlify URL
   (you'll get the exact URL in step 3 — a placeholder is fine for now,
   just come back and fix it).
2. In `render.yaml`, set `FRONTEND_URL` to your Netlify URL and
   `GOOGLE_CALENDAR_REDIRECT_URI` to
   `https://<your-backend>.onrender.com/api/calendar/google/callback`.
   `JWT_SECRET_KEY` is generated by Render. In the Render dashboard, set the
   secrets marked `sync: false`: `INTEGRATION_ENCRYPTION_KEY` (generate with
   the command in `.env.example`) and, to enable Google Calendar,
   `GOOGLE_CALENDAR_CLIENT_ID` / `GOOGLE_CALENDAR_CLIENT_SECRET` from a
   **Web application** OAuth client whose authorized redirect URI is the
   value above. For "Sign in with Google", also set `GOOGLE_LOGIN_CLIENT_ID`
   here and `NEXT_PUBLIC_GOOGLE_CLIENT_ID` on Netlify.
3. Deploy. Watch the `brain-dump-ollama` logs — the first boot pulls the
   model, which can take a while depending on size.
4. Once both are live, hit `https://brain-dump-backend.onrender.com/health`
   — should return `{"status": "ok"}`.

Note on the free/Starter Render plans: they spin down after 15 minutes
of inactivity. Since `scheduler/morning.py` and `scheduler/nightly.py`
need the process alive at 7am/11pm to fire, you want at least a
**Starter (paid, always-on)** plan for `brain-dump-backend`, not Free.

## 3. Frontend — Netlify

1. Netlify dashboard → Add new site → Import an existing project → pick
   the repo.
2. **Base directory:** `frontend` (Netlify needs to know the Next.js app
   isn't at the repo root).
3. Build command / publish directory are already set via
   `frontend/netlify.toml` (`npm run build` / `.next`).
4. Site settings → Environment variables → add
   `NEXT_PUBLIC_API_URL = https://brain-dump-backend.onrender.com` (your
   actual Render URL from step 2).
5. Deploy. Note the resulting `https://<your-site>.netlify.app` URL.
6. Go back to Render, set `ALLOWED_ORIGINS` on `brain-dump-backend` to
   that exact URL, and redeploy the backend so CORS actually allows it.

## 4. Google Calendar OAuth redirect

Milestone 6's OAuth flow was written for a local desktop consent screen.
In Google Cloud Console, under your OAuth client's authorized redirect
URIs, add your Render backend's callback URL (whatever
`backend/integrations/google_calendar.py`'s flow redirects to) so the
consent screen doesn't reject the hosted backend.

## 5. Sanity checklist after both are live

- [ ] `GET /health` on the Render URL returns 200
- [ ] Netlify site loads and its network tab shows requests going to the
      Render URL, not `localhost:8000`
- [ ] A brain-dump submission on the live site actually reaches Ollama
      (check `brain-dump-ollama` logs for an inference call, not just a
      timeout)
- [ ] `ALLOWED_ORIGINS` on Render exactly matches your Netlify URL
      (including `https://`, no trailing slash) or every frontend
      request will fail CORS silently
- [ ] SQLite data survives a manual redeploy (confirms the persistent
      disk is actually mounted at `/data`, not the ephemeral filesystem)
